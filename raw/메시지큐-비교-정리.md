# 메시지 큐 비교 정리 — Redis, Kafka, SQS, RabbitMQ

# Part 1. 각 기술의 동작 메커니즘

비교하기 전에, 각 기술이 내부적으로 어떻게 동작하는지부터 하나씩 뜯어본다. 전체 예시로 "주문이 생성되면 그 이벤트를 재고 서비스가 받아 처리한다"는 시나리오를 계속 사용한다.

## A. Kafka

**토픽(Topic)**
메시지를 종류별로 모아두는 이름표 붙은 큰 통이라고 생각하면 된다. `order-events`라는 토픽을 만들면, 주문 관련 이벤트는 전부 이 토픽으로 들어간다. 이메일 발송 이벤트를 다루고 싶으면 `email-events`라는 별도 토픽을 또 만들면 된다. 하나의 Kafka 클러스터 안에 이런 토픽이 여러 개 있을 수 있다.

**파티션(Partition)**
토픽 하나를 그대로 두면 처리량에 한계가 생긴다(하나의 파일에 순서대로 계속 줄 세워 쓰는 것과 비슷). 그래서 토픽을 여러 개의 **파티션**으로 쪼갠다. `order-events` 토픽을 파티션 3개로 만들면, 들어오는 메시지들이 파티션 0, 1, 2 중 하나로 분산 저장된다. 각 파티션은 그 자체로 "맨 뒤에만 계속 추가되는(append-only) 순서 있는 로그"다 — 엑셀 시트에 행을 계속 아래로만 추가하는 것과 비슷하다.

메시지가 어느 파티션으로 갈지는 보통 **파티션 키**로 결정한다. 예를 들어 주문 ID를 키로 쓰면, 같은 주문 ID를 가진 메시지들은 항상 같은 파티션에 순서대로 쌓인다(그래서 "같은 파티션 안에서는 순서 보장"이라고 하는 것). 반면 서로 다른 주문 ID는 다른 파티션에 흩어질 수 있어서, 파티션을 넘나드는 전체 순서는 보장되지 않는다.

**오프셋(Offset)**
각 파티션 안에서 메시지마다 매겨지는 순번이다(0, 1, 2, 3...). "내가 이 파티션을 오프셋 57까지 읽었다"는 식으로, 컨슈머가 자기 진행 상황을 기억하는 데 쓰인다.

**브로커(Broker)와 클러스터**
브로커는 실제로 파티션 데이터를 디스크에 저장하고 있는 Kafka 서버 한 대를 말한다. 여러 브로커가 모여 하나의 클러스터를 이루고, 파티션들은 여러 브로커에 분산 저장된다. 각 파티션은 리더(leader) 브로커 하나와 복제본(replica)들을 갖는데, 리더가 죽으면 복제본 중 하나가 새 리더가 돼서 데이터 유실을 막는다.

**프로듀서(Producer)와 컨슈머(Consumer)**
프로듀서는 토픽에 메시지를 써 넣는 쪽(주문 서비스), 컨슈머는 토픽에서 메시지를 읽어가는 쪽(재고 서비스)이다. Kafka의 컨슈머는 **pull 방식**이다 — 브로커가 알아서 밀어주는 게 아니라, 컨슈머가 "나 여기서부터 더 읽을 거 있어?" 하고 계속 물어보러 간다(polling). 그리고 중요한 특징: 컨슈머가 메시지를 읽어도 그 메시지는 삭제되지 않는다. 설정된 보존 기간(예: 7일)이나 용량 한도에 도달할 때까지 파티션에 그대로 남아있어서, 필요하면 처음부터 다시 읽는(리플레이) 것도 가능하다. 이게 RabbitMQ/SQS 같은 "먹으면 사라지는" 전통적 큐와 근본적으로 다른 지점이다.

**컨슈머 그룹(Consumer Group)**
같은 그룹에 속한 컨슈머들은 파티션을 서로 나눠 갖는다. 파티션이 3개고 컨슈머가 3개면 1:1로 나눠 갖고, 컨슈머가 5개면 2개는 놀게 된다(파티션 수가 병렬 처리의 상한선). 반면 다른 컨슈머 그룹은 완전히 독립적으로 같은 토픽을 처음부터 다시 읽을 수 있다 — 예를 들어 "재고 서비스" 그룹과 "알림 서비스" 그룹이 각자 독립적으로 `order-events`를 구독하는 식이다.

## B. RabbitMQ

**전체 그림**
RabbitMQ는 Kafka와 정반대에 가까운 철학을 가지고 있다. Kafka가 "단순한 브로커 + 똑똑한 컨슈머(pull)"라면, RabbitMQ는 "똑똑한 브로커(라우팅) + 컨슈머는 그냥 받아서 처리(push)" 쪽에 가깝다.

**익스체인지(Exchange)**
RabbitMQ에서는 프로듀서가 큐에 직접 메시지를 넣지 않는다. 대신 **익스체인지**라는 라우팅 담당자에게 메시지를 던지고, 익스체인지가 규칙에 따라 이걸 어느 큐로 보낼지 결정한다. 익스체인지 종류는 이렇다.

- **direct**: 메시지에 붙은 라우팅 키가 정확히 일치하는 큐로만 보냄(예: "order.created"라는 키를 정확히 구독하는 큐).
- **topic**: 와일드카드 패턴 매칭(예: "order.*"로 구독하면 "order.created", "order.cancelled" 등이 다 걸림).
- **fanout**: 라우팅 키 무시하고 연결된 모든 큐에 브로드캐스트.
- **headers**: 라우팅 키 대신 메시지 헤더 속성으로 매칭.

**바인딩(Binding)**
익스체인지와 큐를 연결하는 규칙("이 익스체인지의 이런 라우팅 키를 가진 메시지는 저 큐로 보내라")이다.

**큐(Queue)**
실제로 메시지가 쌓여서 컨슈머를 기다리는 곳. Kafka의 파티션과 달리, 컨슈머가 메시지를 ack하면 큐에서 그 메시지는 삭제된다.

**컨슈머와 Ack/Nack**
브로커가 큐에 있는 메시지를 컨슈머에게 능동적으로 밀어준다(push). 컨슈머가 처리를 끝내면 ack를 보내야 큐에서 지워지고, 실패하면 nack을 보내 재시도시키거나 DLQ로 보낼 수 있다. **prefetch count**로 "한 번에 몇 개까지 처리 안 끝난 메시지를 컨슈머에게 밀어줄지"를 제한해서, 느린 컨슈머가 메시지에 깔리지 않게 조절한다.

## C. Amazon SQS

**큐(Queue)만 존재한다**
SQS는 Kafka의 토픽/파티션이나 RabbitMQ의 익스체인지 같은 개념이 사용자에게 노출되지 않는다. 그냥 "큐를 하나 만든다"가 전부고, 내부적으로 어떻게 분산 저장되는지는 AWS가 완전히 알아서 처리한다.

**Standard 큐 vs FIFO 큐**
- **Standard**: 순서를 보장하지 않고(best-effort), 중복 전달이 일어날 수 있다. 대신 처리량 제한이 사실상 없다.
- **FIFO**: 이름(`.fifo`로 끝나는 큐 이름) 그대로 순서를 보장한다. 이때 **메시지 그룹 ID**라는 개념이 중요한데, 같은 그룹 ID를 가진 메시지끼리만 순서가 보장되고, 그룹 ID가 다르면 병렬로 처리될 수 있다(Kafka의 파티션 키와 비슷한 발상). 또한 **중복 제거 ID(deduplication ID)**를 지정하면 5분 이내 같은 ID의 중복 발행을 걸러준다.

**폴링(Polling)**
컨슈머는 `ReceiveMessage` API를 호출해서 메시지를 가져간다. Short polling(즉시 응답, 큐가 비어 있으면 빈 응답)과 Long polling(일정 시간 동안 메시지가 올 때까지 기다렸다가 응답, 불필요한 API 호출을 줄여줌) 중 선택할 수 있다.

**가시성 타임아웃(Visibility Timeout)**
컨슈머가 메시지를 받아가면, 그 메시지는 일정 시간 동안 "보이지 않음(invisible)" 상태가 돼서 다른 컨슈머에게는 안 보인다. 이 시간 안에 컨슈머가 `DeleteMessage`(=ack)를 호출하면 큐에서 완전히 삭제된다. 만약 이 시간 안에 삭제하지 않으면(처리 실패, 컨슈머 크래시 등), 메시지는 다시 보이는 상태가 되어 다른 컨슈머가 또 가져갈 수 있다 — 이게 SQS의 재시도 메커니즘이다. 이 재시도가 `maxReceiveCount`를 넘으면 DLQ로 이동한다.

## D. Redis

Redis는 메시징 전용 도구가 아니라 인메모리 자료구조 저장소인데, 그 자료구조 중 일부를 메시징 용도로 쓸 수 있다. **Pub/Sub**과 **Streams**는 완전히 다른 메커니즘이라 따로 이해해야 한다.

**Pub/Sub**
가장 단순한 형태. `PUBLISH 채널이름 메시지`로 특정 채널에 메시지를 보내면, 그 순간 `SUBSCRIBE 채널이름`으로 연결돼 있는 클라이언트들에게 즉시 전달된다. 핵심은 **아무것도 저장하지 않는다**는 것이다. 메시지가 발행되는 순간 구독하고 있는 사람이 없으면, 그 메시지는 그냥 사라진다. 나중에 접속해도 과거 메시지를 받을 방법이 없다. 라디오 방송과 같다 — 방송하는 순간 듣고 있어야 들리지, 나중에 다시 들을 수 없다.

**Streams**
Kafka의 파티션과 비슷한 개념을 Redis 안에 구현한 자료구조다. `XADD 스트림이름 * 필드 값`으로 스트림(하나의 Redis 키)에 항목을 추가하면, 자동으로 `타임스탬프-순번` 형태의 ID가 부여되며 로그처럼 계속 쌓인다. Pub/Sub과 달리 이 데이터는 저장되기 때문에, 나중에 접속해도 `XRANGE`로 과거 데이터를 조회하거나 처음부터 다시 읽을 수 있다.

**컨슈머 그룹(Consumer Group)**: `XGROUP CREATE`로 그룹을 만들고 `XREADGROUP`으로 읽으면, Kafka처럼 여러 컨슈머가 하나의 그룹 안에서 항목을 나눠 처리할 수 있다. 처리 완료 후 `XACK`으로 확인 처리하고, 아직 ack 안 된 항목은 **PEL(Pending Entries List)**이라는 목록에 남아 추적된다(이걸 활용해 직접 DLQ 비슷한 것도 구현 가능).

**저장 방식의 근본적 한계**: 어쨌든 Redis는 기본적으로 인메모리다. RDB 스냅샷이나 AOF 로그로 디스크에 백업하긴 하지만, 이건 Kafka처럼 "디스크 로그가 원본"인 구조가 아니라 "메모리가 원본이고 디스크는 복구용 백업"에 가깝다. 그래서 완전한 내구성을 Kafka만큼 기대하기는 어렵다. 또한 스트림도 계속 추가만 하면 메모리를 무한히 잡아먹으므로 `MAXLEN` 옵션으로 오래된 항목을 잘라내는 관리가 필요하다.

# Part 2. 비교

## 1. 기본 모델 요약

- **Kafka**: 분산 커밋 로그. 컨슈머가 읽어도 메시지가 사라지지 않고, 리플레이가 가능하다.
- **RabbitMQ**: 전통적인 메시지 브로커(AMQP). exchange가 라우팅을 담당하고, 컨슈머가 ack하면 큐에서 메시지가 제거된다.
- **SQS**: 완전관리형 point-to-point 큐. Standard(고성능, 순서 약함)와 FIFO(순서/중복방지 보장, 처리량 제한) 두 종류.
- **Redis**: Pub/Sub(영속성 없는 단순 발행-구독)과 Streams(Kafka와 유사한 로그 기반 구조)로 성격이 완전히 다른 두 도구가 공존.

## 2. 전달 모델과 라우팅

| | 모델 | 라우팅 유연성 |
|---|---|---|
| Kafka | 토픽-파티션, consumer group | 라우팅 로직은 보통 애플리케이션/Kafka Streams가 담당. 브로커 자체 라우팅은 단순 |
| RabbitMQ | 큐 기반, exchange(direct/topic/fanout/headers)로 라우팅 | 가장 유연함. 복잡한 라우팅 토폴로지 구성 가능 |
| SQS | point-to-point 큐 | 단순. 팬아웃이 필요하면 SNS+SQS 조합으로 구현 |
| Redis Pub/Sub | 채널 기반 팬아웃 | 단순. 구독자가 없으면 메시지는 그냥 사라짐 |
| Redis Streams | 로그 기반, consumer group(XREADGROUP) | Kafka와 유사하지만 더 단순 |

## 3. 순서 보장

- **Kafka**: 같은 파티션 안에서는 엄격한 순서 보장. 파티션 간 순서는 보장 안 됨.
- **RabbitMQ**: 단일 큐 안에서는 기본적으로 순서 유지되지만, 여러 컨슈머의 동시 prefetch나 우선순위 큐 사용 시 깨질 수 있다.
- **SQS**: Standard는 순서 보장 없음(best-effort). FIFO는 메시지 그룹 ID 단위로 엄격한 순서 보장.
- **Redis Streams**: 하나의 스트림 안에서는 추가된 순서가 유지된다. Pub/Sub은 영속성이 없어 순서 개념이 실시간 구독 중에만 의미 있다.

## 4. 전달 보장 수준

- **Kafka**: 기본은 at-least-once. idempotent producer + 트랜잭션 API로 Kafka-to-Kafka 파이프라인 내 exactly-once semantics 달성 가능. acks=0이면 at-most-once에 가까움.
- **RabbitMQ**: ack 사용 시 at-least-once, auto-ack 사용 시 at-most-once. 브로커 자체의 exactly-once 보장은 없음.
- **SQS**: Standard는 at-least-once(중복 가능). FIFO는 5분 중복 제거 윈도우 내에서 exactly-once에 준하는 처리 지원.
- **Redis Pub/Sub**: at-most-once(구독자가 없으면 영구 유실). **Redis Streams**: consumer group 사용 시 at-least-once(PEL로 미처리 항목 추적).

## 5. 지속성(영속성)

- **Kafka**: 디스크 기반 로그 + 복제(replication factor)로 내구성 확보. 브로커가 죽어도 디스크 데이터는 안전.
- **RabbitMQ**: durable 큐 + persistent 메시지 옵션을 켜야 재시작에도 살아남는다(기본값 아님). 미러링/쿼럼 큐로 복제 가능.
- **SQS**: 여러 가용영역에 자동 중복 저장돼 내구성이 높음. 보존 기간 최대 14일.
- **Redis**: 기본은 인메모리, RDB/AOF로 베스트 에포트 수준의 영속성만 확보. 설정에 따라 크래시 시 최근 데이터 유실 가능. Streams도 `MAXLEN` 트리밍 없이는 메모리를 계속 점유.

## 6. 처리량과 지연 특성

- **Kafka**: 대용량 스트리밍에 최적화. 배치 처리 기반이라 개별 메시지 지연은 다소 있을 수 있지만 초당 처리량이 압도적.
- **RabbitMQ**: Kafka보다 처리량은 낮지만 메시지 단위 지연이 매우 낮음. 복잡한 라우팅이 필요한 저지연 시나리오에 강함.
- **SQS**: 튜닝 없이도 좋은 처리량. Standard는 사실상 무제한에 가깝고, FIFO는 기본 초당 3,000건(배치)/300건(배치 없음) 수준이며, high throughput 모드를 켜면 API 액션당 최대 70,000 TPS(리전별 상이)까지 확장 가능.
- **Redis**: 인메모리라 지연이 가장 낮음. Pub/Sub과 Streams 모두 처리량은 높지만 Kafka만큼 초대규모 영속 스트리밍에 최적화된 구조는 아님.

## 7. 컨슈머 모델(Push vs Pull)

- **Kafka**: pull. 컨슈머가 poll 루프로 스스로 가져가며 처리 속도를 통제, backpressure 관리가 쉬움.
- **RabbitMQ**: push. 브로커가 밀어주고, prefetch count로 과부하 방지.
- **SQS**: pull(long polling). 컨슈머가 `ReceiveMessage` 호출.
- **Redis Streams**: pull(`XREADGROUP`), Kafka와 유사. Pub/Sub은 push라 그 순간 연결돼 있어야만 수신 가능.

## 8. 확장성

- **Kafka**: 파티션 단위 수평 확장, 대규모 스트리밍 워크로드에 최적화.
- **RabbitMQ**: 클러스터링/페더레이션/샤벨로 확장하지만 Kafka만큼의 초고처리량 확장에는 한계.
- **SQS**: 완전관리형이라 확장을 신경 쓸 필요가 거의 없음. FIFO는 메시지 그룹 단위 처리량 한계만 유의.
- **Redis**: Redis Cluster로 샤딩 확장 가능하지만, 하나의 Stream 키 자체는 자동 샤딩되지 않아 애플리케이션 레벨에서 여러 스트림 키로 나눠야 함.

## 9. 운영 복잡도

- **Kafka**: 셀프 호스팅 시 운영 부담이 가장 큼. 과거엔 ZooKeeper를 별도로 관리해야 했지만, Kafka 4.0(2025년 3월 출시)부터 ZooKeeper가 완전히 제거되고 KRaft가 기본이 되며 부담이 줄었다. 그래도 파티션/레플리카 관리, 리밸런싱 등은 여전히 세심한 튜닝이 필요. Confluent Cloud, AWS MSK 같은 관리형 옵션도 널리 쓰임.
- **RabbitMQ**: 중간 정도 복잡도. 성숙한 툴링이 있지만 대규모 클러스터 운영은 까다로울 수 있음.
- **SQS**: 운영 부담이 사실상 없음. AWS 종속이 유일한 제약.
- **Redis**: 단일 인스턴스는 운영이 단순하지만, 고가용성(Sentinel)이나 샤딩(Cluster)을 갖추려면 복잡도가 늘어남. 메시징 전용 브로커가 아니라 범용 스토어를 메시징에 활용하는 것이라는 점도 감안해야 함.

## 10. DLQ / 재시도 지원 현황

- **SQS**: DLQ가 네이티브로 내장(redrive policy, `maxReceiveCount` 설정만으로 사용 가능). 콘솔에서 DLQ 재처리(redrive) 기능도 제공.
- **RabbitMQ**: `dead-letter-exchange` 설정으로 네이티브 지원. TTL과 조합해 재시도 지연 큐도 직접 구성 가능.
- **Kafka**: DLQ 개념이 브로커에 내장돼 있지 않음. 별도 토픽을 만들고 애플리케이션(또는 Spring Kafka, Kafka Connect)에서 직접 라우팅해야 함.
- **Redis**: DLQ 개념 자체가 없음. Streams를 쓴다면 PEL에서 오래 미처리 상태로 남은 항목을 찾아 별도 스트림으로 옮기는 로직을 직접 구현해야 함.

## 11. Outbox/CDC와의 궁합

- **Kafka**는 Debezium 같은 CDC 도구와의 생태계가 가장 잘 갖춰져 있어 outbox 패턴 구현에 가장 널리 쓰인다(Debezium Outbox Event Router 등).
- **RabbitMQ**는 CDC 연동 사례가 상대적으로 적고, 보통 폴링 방식 릴레이로 outbox를 구현한다.
- **SQS**는 완전관리형이라 CDC로 직접 연동하기보다, 애플리케이션이나 AWS 관리형 커넥터(DMS 등)를 거쳐 발행하는 구조가 흔하다.
- **Redis**는 Streams를 outbox의 발행 대상으로 쓸 수는 있지만, 메시지 보존이 인메모리 기반이라는 근본적 한계 때문에 강한 내구성이 필요한 outbox 목적지로는 잘 쓰이지 않는다.

## 12. 사용 사례 적합성

- **Kafka**: 이벤트 스트리밍, 이벤트 소싱, 로그 집계, 대용량 데이터 파이프라인, 리플레이가 중요한 경우.
- **RabbitMQ**: 전통적인 작업 큐, RPC 스타일 메시징, 복잡한 라우팅이 필요한 경우, 처리량보다 메시지 단위 저지연이 중요한 경우.
- **SQS**: AWS 생태계 안에서 간단히 서비스를 디커플링하고 싶을 때, 서버리스(Lambda 트리거 등)와 연동할 때, 인프라 운영을 전혀 하고 싶지 않을 때.
- **Redis Pub/Sub**: 유실돼도 무방한 실시간 알림(타이핑 표시, 간단한 캐시 무효화 브로드캐스트 등).
- **Redis Streams**: 이미 Redis를 쓰고 있고, Kafka만큼의 운영 부담 없이 가벼운 이벤트 스트리밍이 필요할 때.

## 13. 선택 가이드 요약

| 우선순위 | 적합한 선택 |
|---|---|
| 대용량 스트리밍, 리플레이, 이벤트 소싱 | Kafka |
| 복잡한 라우팅, 낮은 메시지 단위 지연 | RabbitMQ |
| AWS 환경에서 최소 운영 부담 | SQS |
| 이미 Redis를 쓰고 있고 가벼운 용도 | Redis Streams(영속성 필요) / Pub/Sub(유실 허용) |
| 강한 순서 보장이 서비스 전체에 필요 | Kafka(파티션 키) 또는 SQS FIFO |
| DLQ를 바로 쓰고 싶음(구현 최소화) | SQS 또는 RabbitMQ |
| outbox + CDC 생태계 활용 | Kafka(Debezium) |
